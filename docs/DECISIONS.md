# Decisions

One line each: decision, why.

- One pnpm monorepo instead of the 11 repos in scope §4: four people, one shared contracts package, simpler CI and reviews.
- Packages are named `@sdd/<name>` and export their TypeScript source (`exports: ./src/index.ts`) with no build step: fastest feedback for a small team; Vitest and Next (`transpilePackages`) compile it directly.
- Dependency versions are pinned exactly (`.npmrc: save-exact=true`): reproducible installs, no surprise upgrades before the demo.
- TypeScript is pinned to 5.9.3, the version the prototype was built and tested on: 7.x resolved by default but is unverified with the rest of the toolchain.
- Tree-sitter native build scripts are disabled (`allowBuilds: false` in `pnpm-workspace.yaml`): the code loads the `.wasm` grammars through `web-tree-sitter`, so the native addons are never used.
- The tree-sitter `.wasm` files are located with `require.resolve` from the package instead of `process.cwd()/node_modules`: the old path breaks as soon as the code runs from another directory or under pnpm's layout.
- Tests locate fixtures with `import.meta.dirname` instead of `process.cwd()`: tests then pass from the repo root and from the package directory.
- `.gitattributes` forces LF line endings: the team uses mixed platforms and Prettier expects LF.
- The Next.js console loads the repo-root `.env` in `next.config.mjs`: one `.env` for the whole repo; variables already in the environment still win.
- `repos.config.json` and `output/` stay relative to the console app's working directory for now: Phase 4 replaces the hand-edited config with the repo profiler.
- Prettier uses `printWidth: 140`: it matches the prototype's existing style and keeps the formatting diff small.
- `llm`, `orchestrator`, `agents`, `mcp-server`, `ui` and `eval` are empty placeholder packages so teammates can start against stable names; each is filled by its owner (see `docs/TEAM.md`).
- Postgres runs only in Docker (`pgvector/pgvector:pg16`, bound to 127.0.0.1:5432, healthchecked) and is managed through `pnpm db:*` scripts: every teammate gets the same database with no local install.
- Contracts use Zod 4.6.7 and are Zod-first (types are inferred): one definition feeds validation, LLM tool schemas (`z.toJSONSchema`) and `docs/API.md`.
- The state machine is the 13-status subset requested for this project. `SPEC_REVIEW` from scope §5 is dropped: `REQUIREMENT_REVIEWED` already means "no gaps, waiting for Product's final approval". `BACKLOG`, `READY_FOR_REVIEW`, `QA_VALIDATION` and `READY_FOR_RELEASE` are cut with the Review/Validation Agent and release flow.
- `REQUIREMENT_REVIEW -> REQUIREMENT_REVIEWED` is not a direct transition: after Product answers, the agent re-runs (`REQUIREMENT_GENERATING`) and only the agent finding no remaining gaps can reach `REQUIREMENT_REVIEWED`. Product can also send `REQUIREMENT_REVIEWED` back to `REQUIREMENT_GENERATING` to request changes.
- Actors are `orchestrator | product | architecture | developer`. There is deliberately no agent actor: agents propose, the orchestrator transitions, humans approve (scope §11). Only Product can reach `SPEC_APPROVED`; only Architecture can reach `DESIGN_APPROVED` or `DESIGN_REVISION_REQUESTED`.
- "Generate tasks only after both approvals are recorded" is a precondition on the `DESIGN_APPROVED -> TASKS_GENERATING` transition that the orchestrator must check against stored approvals; the state machine only enforces the order of statuses.
- Within one initiative, references are readable ids (`AC-1`, `FR-1`, `NFR-1`, `DS-1`, `T-1`) instead of UUIDs: agents can cite them reliably and humans can read them. They are unique per initiative (per tasks artifact for `T-n`), so database tables need a composite key with `initiativeId`.
- Acceptance criteria are `{ id, text }` objects so tasks can reference them (`acceptanceCriterionRefs`); the create-initiative request can still accept plain strings and assign the ids.
- Requirements, design and tasks are stored as one artifact-version shape (`kind`, `version`, structured `content`, rendered `markdown`, `needsHumanMerge`), matching the single "artifact versions" table in the migrations issue. Markdown is always rendered from `content`.
- `Task` gets `title` and `status` (`todo | in_progress | done`) beyond the fields listed in the plan: tasks.md needs a heading and the MCP server needs to report progress.
- `ClarificationQuestion` and `Approval` carry a `stage` (`requirements | design`) because scope §2 has the Design Agent raising questions too; `Approval` records the `artifactVersion` it applies to.
- `AgentRun.status` is `succeeded | failed` (the row is written after the call finishes) and `initiativeId` is optional so indexing runs can be recorded too.
- `ContextBundle` keeps the prototype's field names and adds `mode`, `tokenEstimate` and `truncated`; chunks use `repoId` (the prototype's `repoName`). `EMPTY_CONTEXT_BUNDLE` is what Case A's provider returns.
- `docs/API.md` is generated, not written: the endpoint registry in `packages/contracts/src/endpoints.ts` (method, path, schemas, examples, error rows) is the single source for the doc, the server routes and the UI mock API. `pnpm docs:api` writes it, `pnpm docs:api:check` fails on drift (for CI), and a unit test fails `pnpm test` too. The file is excluded from Prettier so formatting cannot cause false drift.
- Every example in the API doc is typed against its schema and parsed with it when the doc is generated: an example cannot describe a shape the API does not return.
- `tsx` (dev only, contracts package) runs the doc generator; esbuild's install script is disabled because its binary comes from a platform package.
- Creating an initiative also starts the workflow (`READY_FOR_SPEC -> REQUIREMENT_GENERATING`, triggered as `product`); there is no separate start endpoint. Creation is Product confirming the requirement is ready.
- Agents run in the background: calls that start one return at once with a `*_GENERATING` status (repos: `profiling` / `indexing`) and clients poll. Server-sent events or webhooks are future work.
- The stage in approve and request-changes decides the actor: `requirements` is Product, `design` is Architecture. After a decision the orchestrator immediately starts the next agent, so the response usually already shows `DESIGN_GENERATING` or `TASKS_GENERATING`.
- Answers: all open requirements questions must be answered before the agent re-runs; design-stage answers are stored and used on the next change request; an answered question cannot be answered again.
- Errors use one envelope with five codes: `validation_error` 400 (Zod issues in `details`), `not_found` 404, `invalid_transition` 409, `conflict` 409, `internal_error` 500.
- Repo ids are lowercase slugs derived from the name, and `Initiative.repoId` is that slug. Repos go `profiling -> profiled -> indexing -> indexed` (or `failed`). Registering returns 202 and profiles in the background; indexing is a separate call so a person can look at the recommendation first.
- Scope §6.1 gives no rule for repos between 200 and 999 files (full pipeline at 1000+, CLAUDE.md only under 200). The profiler thresholds are decided in the Context Agent PR and recorded here.
- No endpoint yet lets a human edit an artifact's markdown. `needsHumanMerge` is in the contract; the edit and merge endpoints are added with the merge flow in Phase 5.
- There is no authentication yet; `reviewer` is a free-form string.
- `@sdd/llm` is the only module that imports `@anthropic-ai/sdk` (enforced by an ESLint `no-restricted-imports` rule). It also owns the Voyage embeddings client, so every model and embedding call produces a usage record.
- Forced tool use is only used on models that still accept it. `claude-sonnet-5-5` (our production default), `claude-opus-5-5`, `claude-fable-5-1` and `claude-mythos-5-1` return HTTP 400 for `tool_choice` `tool`/`any`, so those models get `tool_choice: auto`, an explicit "call the tool" instruction, Zod validation and the single retry. The allow-list lives in `packages/llm/src/models.ts`; unknown models default to the safe `auto` path.
- The gateway sends no `temperature`/`top_p`/`top_k`/`budget_tokens` (rejected by the newer models) and does not use strict tool schemas (they reject the length and range limits our entity schemas rely on); Zod does the validating.
- The validation retry is a fresh single-turn request with the validation errors and the previous answer appended to the input, not a replayed conversation: it works on every model and avoids the thinking-block replay rules.
- Structured output cut off at `maxTokens` and refusals are not retried (a retry would hit the same limit or refusal); they throw `LlmTruncatedError` / `LlmRefusalError`. Truncated _text_ is returned with `truncated: true` so callers decide.
- `onUsage` fires once per billed request (a validation retry produces two rows) so recorded cost equals real spend. A throwing hook fails the call so a cost row is never silently lost.
- Default model: the call's `model`, else `LLM_MODEL` (the prototype's `SDD_MODEL` and `CLAUDE_MODEL` are gone), else `claude-sonnet-5-5` in production and `claude-haiku-5-5` otherwise. Real evaluation runs must set `LLM_MODEL` explicitly.
- Prices are a versioned table (`PRICE_TABLE_VERSION`, snapshot 2026-10-06) and a model without a price is rejected before the call: cost is never silently $0. Costs are estimates for budgeting, not invoices.
- Mock mode is strict for structured calls (missing fixture throws, invalid fixture throws) and lenient for prose (`generateText` returns a marked placeholder), and the mock embeddings are feature-hashed word pieces so offline retrieval ranking is meaningful.
- Recording fixtures (`LLM_MODE=record`) lets a developer with a key produce the fixtures that CI replays; fixtures are keyed by a hash of (agent, call name, input), so editing a prompt's input invalidates its fixture on purpose.
- `wrapUntrusted` rejects oversize text instead of truncating (silent truncation hides requirement text from the model), uses content-hash markers so a block cannot be closed from inside, and is deterministic so fixture keys stay stable.
- The platform calls the Claude API directly. The prototype's Bedrock path (`LLM_PROVIDER`, `BEDROCK_API_KEY`, `AWS_REGION`) is removed, not folded into the gateway: one provider means one set of credentials, prices and failure modes to test.
